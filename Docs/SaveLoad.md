# 칠판 저장·불러오기 구현 설명

이 문서는 그림만 보관하는 `.chalk` 버전 2 형식과 호출 흐름을 설명합니다. 분필 색·굵기, 지우개 크기 같은 도구 설정은 파일에 기록하지 않으며, 전체 열기와 추가 불러오기 모두 현재 설정을 유지합니다. 이미 그린 선의 색과 굵기는 RGBA 픽셀에 반영되어 있으므로 별도 도구 설정 없이 그대로 복원됩니다.

## 1. 무엇을 저장하는가

칠판 그림의 원본은 GPU 화면이 아니라 `BoardCanvas::layers_`에 있는 CPU 픽셀 데이터입니다.

```cpp
using Layer = std::vector<std::uint32_t>;
std::vector<Layer> layers_;
```

레이어 하나는 `1536 × 720 = 1,105,920`개 픽셀을 보관합니다. 좌표 `(x,y)`의 배열 위치는 `y * Width + x`입니다. 예를 들어 다음 위치들은 같은 가로 행에 있습니다.

```text
(0,0) → 배열 0번
(1,0) → 배열 1번
(0,1) → 배열 1536번
```

픽셀 하나는 32비트 정수입니다. 정수 표기는 `0xAABBGGRR`이며, Windows Little Endian 메모리에서 바이트 순서는 `R,G,B,A`입니다.

| 픽셀 | RGBA | 저장 정수 |
|---|---|---|
| 빈 곳 / 완전히 지운 곳 | (0,0,0,0) | `0x00000000` |
| 빨간 분필 | (255,0,0,255) | `0xFF0000FF` |
| 초록 분필 | (0,255,0,255) | `0xFF00FF00` |
| 파란 분필 | (0,0,255,255) | `0xFFFF0000` |

현재 편집기는 빈 픽셀 또는 Alpha=255인 픽셀만 원본에 저장합니다. 브러시 안에 들어온 픽셀은 불투명하게 기록하고, 지우개 안의 픽셀은 **모든 레이어에서 값 전체를 0**으로 바꿉니다. 별도의 지우개 마스크로 숨기는 방식이 아닙니다.

초록색 판, 나무 테두리, Collider, UI는 그림 파일에 들어가지 않습니다. 초록색은 `BoardScene`의 앞면 색상이고, 그림 텍스처에서 빈 곳을 통해 그 바탕이 보입니다.

## 2. 담당 코드

| 코드 | 역할 |
|---|---|
| `BoardScene::RegisterUI()` | 저장/열기/추가 버튼을 함수에 연결 |
| `Application::Update()` | Ctrl+S, Ctrl+O, Ctrl+Shift+O 단축키 연결 |
| `BoardScene::ChooseFile()` | Windows 파일 선택 창에서 경로 얻기 |

| `BoardCanvas::Save()` | 헤더, 레이어 체크섬, 압축 픽셀을 바이너리로 쓰기 |
| `BoardCanvas::Load()` | 파일 해석, 크기/값/체크섬 검사, 레이어 복원 |
| `BoardScene::LoadDialog()` | 검증된 문서를 전체 열기 또는 위에 추가하기 |

| `BoardCanvas::Composite()` | 아래→위 순서로 그림을 화면용 픽셀에 합성 |

직렬화 코드는 `Source/Features/Chalkboard/BoardCanvas.cpp`, 사용자 동작 연결은 `BoardScene.cpp`에 있습니다.

## 3. 저장 파일의 정확한 구조

확장자는 `.chalk`이며 PNG나 JSON으로 이름만 바꾼 것이 아닌 자체 바이너리 형식입니다.

```text
24바이트 고정 헤더
레이어 0: 체크섬 + 압축 픽셀
레이어 1: 체크섬 + 압축 픽셀
...
레이어 N-1: 체크섬 + 압축 픽셀
```

헤더의 식별 문자열을 제외한 정수는 모두 4바이트 `uint32`이며 Little Endian입니다.

| 파일 시작에서의 위치 | 크기 | 내용 | 현재 값 또는 의미 |
|---|---:|---|---|
| 0 | 8바이트 | 파일 식별 문자열 | `DXCHALK1` |
| 8 | 4바이트 | 버전 | `2` |
| 12 | 4바이트 | 캔버스 너비 | `1536` |
| 16 | 4바이트 | 캔버스 높이 | `720` |
| 20 | 4바이트 | 레이어 수 | `1~24` |

첫 레이어의 체크섬은 파일 시작에서 24바이트 위치에 이어집니다. 식별 문자열 `DXCHALK1`은 기존 형식과 공유하며, 별도의 버전 필드가 실제 데이터 구조를 구분합니다.

이전 버전 1에는 레이어 수 뒤에 분필 색·굵기·지우개 크기 12바이트가 더 있어 헤더가 36바이트였습니다. 현재 로더는 그 12바이트를 읽어 건너뛰고 그림만 복원합니다. 새 저장은 항상 버전 2로 하므로 예전 파일을 열어 다시 저장하면 도구 설정은 제거됩니다. 이전 실행 파일은 버전 2 파일을 지원하지 않습니다.

`Put()`은 정수를 낮은 바이트부터 하나씩 기록하고 `Get()`은 그 역순서로 조립합니다. C++ 객체나 구조체의 메모리를 통째로 쓰지 않으므로 포인터 값, 클래스 내부 구조, 패딩은 파일에 섞이지 않습니다.

레이어 배열의 0번은 가장 아래이며 마지막 원소는 가장 위입니다. `Save()`가 그 순서 그대로 파일에 기록하여 다시 열었을 때 겹침 순서를 복원합니다.

레이어마다 먼저 압축 전 픽셀의 FNV-1a 32비트 체크섬 4바이트를 쓰고, 다음과 같은 압축 쌍을 이어서 기록합니다.

```text
반복 횟수(uint32, 4바이트) + 픽셀 RGBA(uint32, 4바이트)
```

레이어별 Run 개수나 끝 표시를 별도로 넣지 않습니다. 읽는 쪽에서 정확히 1,105,920개 픽셀을 복원하면 해당 레이어가 끝나고 다음 레이어의 체크섬을 읽습니다.

## 4. 픽셀 압축은 어떻게 하는가

사용한 방식은 RLE(Run-Length Encoding)입니다. 배열에서 **같은 색이 연속되는 길이**와 **그 색**만 기록합니다.

```text
원본: [빈 곳, 빈 곳, 빈 곳, 빨강, 빨강, 파랑]
압축: [(3, 빈 곳), (2, 빨강), (1, 파랑)]
```

`Save()`의 `i`는 현재 Run 시작이고 `end`는 같은 색 구간의 끝입니다.

```cpp
const auto pixel=layer[i];
std::size_t end=i+1;
while(end<PixelCount&&layer[end]==pixel)++end;
Put(out,static_cast<std::uint32_t>(end-i));
Put(out,pixel);
i=end;
```

전체가 빈 레이어는 `(1,105,920, 0)`이라는 8바이트 쌍 하나면 됩니다. 빈 레이어 한 개만 있는 문서는 헤더 24 + 체크섬 4 + Run 8 = **36바이트**입니다. 압축하지 않으면 레이어 픽셀만 4,423,680바이트가 필요합니다.

가로 행 경계를 넘어 같은 값이 이어져도 한 Run으로 기록합니다. 배열을 같은 순서로 복원하므로 문제가 없습니다. 색이 매 픽셀마다 바뀌는 그림은 Run당 8바이트가 필요하여 압축 전보다 커질 수 있습니다. RLE가 모든 그림을 더 작게 만드는 것은 아닙니다.

## 5. 저장 버튼을 누르면 어떤 순서로 실행되는가

```text
저장 버튼 / Ctrl+S
    ↓
SaveDialog → ChooseFile(true)
    ↓
선택 경로 옆에 Board.chalk.<시간값>.tmp 생성
    ↓
canvas.Save(임시 경로)
    ├─ 헤더 기록
    ├─ 아래→위 레이어 체크섬과 RLE 기록
    └─ flush / close 성공 검사
    ↓
MoveFileExW로 임시 완성본을 최종 경로로 교체
    ↓
canvas.MarkSaved() / 화면에 저장 완료 표시
```

`BoardCanvas::Save()` 자체는 전달받은 파일을 `trunc`로 새로 씁니다. 따라서 기존 저장본을 보호하는 것은 **SaveDialog가 최종 경로 대신 임시 경로를 넘기는 부분**입니다. Save를 직접 호출하면 이 임시 교체 단계는 적용되지 않습니다.

기록 실패 시 임시 파일만 정리하고 기존 저장본은 유지합니다. 최종 파일 교체에도 성공한 뒤 `dirty_`를 false로 바꿉니다. PNG 내보내기는 편집용 저장과 다르므로 이 플래그를 내리지 않습니다.

Windows 교체 옵션은 `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`입니다. 같은 폴더에 완성본을 먼저 준비하여 쓰다가 실패한 파일을 기존 저장본으로 노출할 가능성을 줄입니다. 이 절차는 장치 고장이나 모든 전원 장애에서 복구를 보장하는 백업은 아닙니다.

## 6. 불러올 때는 어떻게 복원하는가

`LoadDialog()`는 기존 `canvas`에 바로 읽지 않고 별도 `BoardCanvas loaded`를 만듭니다.

```text
파일 선택 → loaded.Load(path) → 파일 전체 검증 → 성공한 문서만 반영
```

`Load()` 안에서도 로컬 `Snapshot loaded`에 복원한 레이어를 모읍니다. 파일을 읽다가 현재 그림을 조금씩 덮어쓰는 구조가 아닙니다.

검사 순서는 다음과 같습니다.

1. 파일이 열리는지와 `DXCHALK1` 식별 문자열 확인.
2. 헤더를 끝까지 읽을 수 있는지 확인.
3. 지원 버전(1 또는 2), 1536×720 고정 크기, 레이어 1~24개 확인. 버전 1이면 이전 도구 설정 12바이트를 읽어 건너뛰며 값은 적용하지 않음. 이 필드가 잘린 파일은 거부.
4. 각 Run이 끝까지 읽히는지 확인.
5. Run 길이가 0이 아니고 레이어의 남은 픽셀 수를 넘지 않는지 확인.
6. 빈 픽셀 전체 0 또는 Alpha=255 픽셀인지 확인.
7. 복원한 레이어 픽셀의 체크섬을 파일의 체크섬과 비교.
8. 모든 레이어 뒤에 불필요한 데이터가 남지 않는지 확인.

검사에 실패하면 즉시 false를 반환합니다. 모든 검사가 끝난 다음에만 아래 반영이 실행됩니다.

```cpp
layers_=std::move(loaded);
undo_.clear();
redo_.clear();
```

도구 설정은 변경하지 않고, 파일에서 막 읽은 그림이므로 저장 필요 상태는 해제합니다. CPU 합성 결과와 GPU 텍스처는 이전 문서의 내용일 수 있으므로 두 캐시의 갱신 플래그를 다시 켭니다. 다음 Render에서 `Composite()`와 `UpdateSubresource()`가 실행되어 화면이 바뀝니다.

체크섬은 레이어의 압축 전 RGBA에 적용하며 헤더는 포함하지 않습니다. 헤더는 값의 범위를 검사합니다. FNV-1a는 일반적인 손상 탐지용이지 암호화/보안 인증이 아니며 체크섬 충돌도 가능합니다.

## 7. 전체 열기와 추가 불러오기의 차이

### 전체 열기: LoadDialog(false)

`LoadDialog()`가 임시 객체 `loaded`에 현재 분필 색·굵기·지우개 크기·지우개 선택 상태를 먼저 복사합니다. `Load()`는 그림만 복원하므로 이 설정은 유지됩니다. 검증한 다음 기존 변경을 버릴지 확인하고 `canvas=std::move(loaded)`로 교체합니다. 결과적으로 그림은 저장본 기준이 되고 도구는 사용하던 설정 그대로입니다. 실행 취소 이력은 복원하지 않으며, 전체 열기를 Undo로 되돌리지는 않습니다.

### 위에 추가: LoadDialog(true)

`canvas.Append(loaded,error)`를 호출합니다. 기존 그림과 도구 설정을 유지하며, 가져온 문서의 비어 있지 않은 레이어만 현재 배열 뒤에 복사합니다. 이때 기존 맨 위의 빈 작업 레이어는 제거하고, 추가가 끝난 뒤 새 빈 작업 레이어를 하나 만듭니다.

```text
기존: [A의 그림, 빈 작업 레이어]
B 추가: [A의 그림, B의 그림, 새 빈 작업 레이어]
C 추가: [A의 그림, B의 그림, C의 그림, 새 빈 작업 레이어]
```

`Composite()`는 아래부터 순서대로 보며 Alpha가 있는 픽셀만 결과에 대입합니다. 따라서 A와 B의 같은 위치에 그림이 있으면 나중에 읽은 B가 보이고, B가 빈 곳에서는 A가 보입니다. 불러올 때 실제 3D 면을 앞뒤로 움직이는 것이 아니라 **레이어의 합성 순서**로 위아래를 결정합니다.

새 필기는 마지막 빈 작업 레이어에 기록되어 C보다 위에 표시됩니다. 추가 불러오기 자체는 한 번의 실행 취소 작업이며, 레이어 상한을 넘거나 저장본에 그림이 없으면 현재 문서를 변경하지 않고 거부합니다.

## 8. 지운 데이터도 저장되는가

지우개가 닿으면 해당 좌표의 모든 레이어 값을 0으로 바꾸고, 저장은 그 변경된 픽셀 배열을 읽습니다. 따라서 지운 곳은 파일에도 0으로 들어갑니다. 다시 열거나 다른 문서 위에 추가해도 그 파일에 이전 RGB가 숨어 있지 않습니다.

실행 취소용 스냅샷에는 편집 전 그림이 메모리로 남을 수 있지만 `.chalk`에는 스냅샷을 저장하지 않습니다. 이미 따로 저장해 둔 과거 파일까지 지우개로 수정하는 것은 아니므로, 예전 저장본을 다시 가져오면 그 파일의 그림은 다시 나타납니다.

## 9. .chalk와 PNG의 차이 및 현재 범위

| 항목 | .chalk | PNG 내보내기 |
|---|---|---|
| 레이어 순서/개별 픽셀 | 보존 | 최종 합성 결과만 보존 |
| 분필 색·굵기/지우개 크기 | 저장하지 않음 | 저장하지 않음 |
| 초록색 판/나무/UI | 없음 | 없음 |
| 빈 곳의 투명도 | 보존 | 보존 |
| 앱에서 다시 불러오기 | 지원 | 현재 미지원 |

PNG는 `ImageFile::WritePng()`에서 WIC가 지원하는 BGRA 바이트 순서로 변환하여 저장합니다. Alpha는 보존합니다. 이것은 파일 인코더 형식에 맞추는 작업으로, 분필 RGB를 다른 색으로 바꾸는 작업은 아닙니다.

현재 저장하지 않는 것은 모든 도구 설정, 카메라 위치, Collider, UI 패널 위치, Undo/Redo입니다. 파일 열기 시 분필 색·굵기·지우개 크기·지우개 선택 상태는 현재 값을 유지합니다. 도구 설정만 바꾸면 저장 파일 내용은 달라지지 않습니다. 자동 저장은 하지 않습니다. 다른 해상도·버전·부분 Alpha 레이어를 지원하려면 포맷 버전과 로더/합성기를 함께 확장해야 합니다.

관련 테스트는 `Tests/ChalkboardTests.cpp`의 DocumentTests와 Preview에 있습니다. 픽셀/레이어 순서의 저장 후 복원, 도구 변경 전후 저장 바이트 일치, 불러오기 시 현재 도구 유지, 이전 버전 파일 호환과 설정 무시, 손상 파일 거부, 레이어 상한, 지운 RGBA 및 PNG 색상/투명도 복원을 검사합니다.
